## 📖 Что изменилось

Craftbook v2 меняет **смысл стандарта**, а не только структуру каталогов. В v1 акцент был на строгих правилах реализации и DDD; v2 ориентирован на корректность Rust, безопасность абстракций, явные контракты проекта и необязательные архитектурные профили.

| Требование v1 | Подход v2 |
|---|---|
| Один основной тип на файл | Связные модули с любым разумным количеством элементов |
| Фиксированные пределы строк, функций и глубины модулей | Размер и сложность — сигналы для ревью |
| DDD-слои в каждом проекте | Необязательные профили DDD, Hexagonal, акторы, системный код, производительность |
| Один ограниченный контекст на доменный crate | Контексты не обязаны совпадать с границами crates |
| Весь ввод-вывод только через порты | Порты там, где изоляция действительно полезна |
| Универсальные требования `Send + Sync` или `Clone` | Реализовать трейты только при наличии смысла |
| Обязательные проценты покрытия и мутационного тестирования | Проверка по рискам и явным требованиям проекта |
| Обязательный старый Python-анализатор | Нативный Rust-инструмент для политики v2; старый — для сравнения |

## 🚀 Этапы миграции

1. **Зафиксируйте текущее поведение.** Сохраните собираемые версии, контракты публичного API, конфигурацию развертывания, известные метрики и прежние исходные показатели.
2. **Пересмотрите проверки.** Уберите безусловные ошибки, связанные лишь с числом строк, глубиной модулей, запретами имён, процентами покрытия или обязательными DDD-слоями.
3. **Выберите нужные профили.** Архитектура должна учитывать предметную область, среду исполнения, оборудование, требования безопасности и производительность.
4. **Создайте политику v2.** Возьмите [пример](templates/CraftBook.toml), укажите проект и профили. Не переносите карту слоёв v1 механически.
5. **Сохраните полезные проверки.** Продолжайте использовать rustfmt, rustc, Clippy, подходящие тесты и проверки совместимости или безопасности.
6. **Переходите постепенно.** Сохраняйте полезные агрегаты, порты и адаптеры; переписывайте код только при выявленных проблемах. Изменения поведения защищайте регрессионными и контрактными тестами.
7. **Документируйте решения.** Существенные решения по API, транзакциям, зависимостям, форматам данных и производительности фиксируйте в ADR или документации проекта.
8. **Проверьте целевые платформы.** Перед отключением старых проверок протестируйте поддерживаемые сочетания возможностей сборки, платформы, параметры релиза и поведение системы.

Не объединяйте crates и не уплощайте структуру модулей автоматически лишь потому, что первоначальная архитектура следовала DDD.

## 🛠️ Инструменты

Новая экспериментальная утилита на Rust проверяет конфигурацию v2:

```bash
cargo install --path tools/cargo-craftcheck
cargo craftcheck check --config templates/CraftBook.toml
```

Она **пока не анализирует архитектуру исходного Rust-кода и граф зависимостей Cargo**. Старый `tools/craftcheck` можно использовать для сравнения результатов v1, но его диагностика не является обязательной для v2.

Проверка самой новой утилиты:

```bash
cargo fmt --all --check --manifest-path tools/cargo-craftcheck/Cargo.toml
cargo clippy --all-targets --manifest-path tools/cargo-craftcheck/Cargo.toml -- -D warnings
cargo test --manifest-path tools/cargo-craftcheck/Cargo.toml
```

## 🔐 Совместимость

Прохождение проверки политики ещё не означает завершение миграции. При необходимости проверьте публичные контракты, сериализацию, хранение данных, поведение на целевых платформах, ошибки, освобождение ресурсов и производительность. Явно заданные и обоснованные требования проекта остаются обязательными.

Старые отчёты внедрения — исторические снимки состояния; перед использованием показателей их нужно измерить заново.
