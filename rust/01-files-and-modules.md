# 1. Files and modules

A file is a unit of reading. Somebody opening it should see one thing, named
by the file, with nothing else competing for attention. This chapter is the
Rust counterpart of the C# rule "one type per file, the file named after the
type, the folder named after the namespace".

## 1.1 Limits

| What | Target | Hard limit |
|---|---|---|
| Production lines in a `.rs` file (everything except its `#[cfg(test)] mod tests { … }`) | ≤ 250 | **400** |
| Lines in an inline `#[cfg(test)] mod tests { … }` | ≤ 150 | **150**, then `tests.rs` |
| `lib.rs` / `mod.rs` of a module that has submodules | ≤ 60 | **100**, and no logic (§1.4) |
| `.rs` files directly inside one module directory (not counting `mod.rs`, `tests.rs`) | ≤ 7 | **12**, then group into submodules |
| Module depth below `src/` | ≤ 3 | **4** |

Lines are physical lines, including docs and blank lines: the reader scrolls
through all of them. The only exemptions are files that say in their first
line that they are generated (`// @generated by <tool>`), and data tables whose
file name ends in `_table.rs` (a lookup table, a WGSL source string). An
exemption is never claimed for hand-written logic.

**Why these numbers.** A 400-line file is about eight screens; above that,
nobody holds it in their head and review quality collapses. 250 is what one
responsibility usually takes in Rust once tests are moved out.

## 1.2 One primary item per file

Every file has exactly one **primary item**, and the file is named after it in
`snake_case`:

| File | Primary item |
|---|---|
| `render_graph.rs` | `pub struct RenderGraph` |
| `decode_error.rs` | `pub enum DecodeError` |
| `rotation.rs` | `pub trait Rotation` or a cohesive family of free functions about rotation |

The file may also hold **companions** of the primary item, and nothing else:

- its error type, if only this item returns it;
- its builder, iterator, guard or view types (`RenderGraphBuilder`, `Iter<'a>`);
- private helper types and functions it uses.

A second type that has callers of its own is not a companion: it gets its own
file. A file that needs the word "and" to describe it (`mesh_and_material.rs`)
is two files.

## 1.3 When to split into submodules

Split **before** a hard limit is reached, at the first of these:

1. A file approaches 250 production lines and has more than one reason to
   change (two responsibilities, two audiences, two kinds of caller).
2. A type's `impl` has a group of methods that only touch a subset of its
   fields. That subset is a type of its own (§2 of the functions chapter).
3. Three or more files in a directory share a prefix or a word
   (`mesh_registry.rs`, `mesh_bake.rs`, `mesh_upload.rs`): that word is a
   module, `mesh/`, holding `registry.rs`, `bake.rs`, `upload.rs`.
4. A type has variants per platform, per back end or per numeric flavour:
   one submodule per variant, behind a trait or `cfg` in `mod.rs`.
5. Tests for a module exceed 150 lines: the module becomes a directory with a
   `tests.rs` next to `mod.rs`.

How a module becomes a directory:

```text
src/
  lib.rs              // wiring only
  scene/
    mod.rs            // wiring only: mod + pub use
    camera.rs         // pub struct Camera
    light.rs          // pub enum Light
    renderable.rs     // pub struct Renderable
    tests.rs          // #[cfg(test)] mod tests;  (declared in mod.rs)
```

- Use `foo/mod.rs`, not `foo.rs` next to `foo/`. One style everywhere: the
  module and everything in it moves, renames and deletes as one directory.
- Never split by kind of item (`types.rs`, `traits.rs`, `utils.rs`,
  `helpers.rs`, `common.rs`, `misc.rs`). Split by responsibility. A `util`
  module is where responsibilities go to be forgotten; these names are
  rejected in review.
- A module with a single file inside it is not a module; fold it back.

## 1.4 `lib.rs` and `mod.rs` are wiring

Once a module has submodules, its `lib.rs` / `mod.rs` contains only:

1. the `//!` module documentation;
2. `mod` declarations (with their `cfg` attributes);
3. `pub use` re-exports that form the module's public surface;
4. a crate-level `#![…]` attribute block (in `lib.rs`).

No `fn`, no `impl`, no `struct`/`enum`/`trait` definitions, no `const`
values. It is the table of contents of the module, the analogue of a C#
project file plus the namespace's public types.

A crate small enough to be one file (≤ 250 lines) may keep its code in
`lib.rs`. The day it grows a second file, `lib.rs` becomes wiring.

## 1.5 Public surface and re-exports

- Submodules are private (`mod camera;`) and their public items are
  re-exported from the parent (`pub use camera::Camera;`). Callers write
  `meridian_graphics::Camera`, not `meridian_graphics::scene::camera::Camera`.
- A submodule is `pub mod` only when its name is part of the vocabulary the
  caller should see (`git::status`, `git::branch`), the same way a C#
  namespace is.
- No glob re-exports (`pub use foo::*`) except a crate's `prelude` module.
- No glob imports (`use foo::*`) outside `prelude` and `tests` modules
  (`use super::*;` in tests is fine).

## 1.6 Where tests live

| Kind | Where |
|---|---|
| Unit tests of a file, ≤ 150 lines | `#[cfg(test)] mod tests { … }` at the bottom of that file |
| Unit tests of a module, > 150 lines | `tests.rs` in the module directory, declared `#[cfg(test)] mod tests;` in `mod.rs`; split further into `tests/<topic>.rs` when it passes 400 |
| Integration tests of a crate's public API | `tests/<behaviour>.rs` in the crate |
| Shared test fixtures and fakes | a `testing` module behind `#[cfg(any(test, feature = "testing"))]`, never in production builds |
| Benchmarks | `benches/` with `criterion` |

Testing rules themselves are in [chapter 8](08-testing-and-quality.md).

## 1.7 Item order inside a file

Same order in every file, so readers know where to look:

1. `//!` module doc;
2. `use` declarations: `std`/`core`/`alloc`, then external crates, then
   `crate::`/`super::` — one group each, separated by a blank line
   (nightly `rustfmt` enforces it with `group_imports = "StdExternalCrate"`,
   see [tooling](06-tooling.md));
3. `const` and `static` items;
4. the primary item: its definition, then its inherent `impl`, then its trait
   `impl`s (std traits first: `Default`, `Display`, `From`…, then crate
   traits);
5. companions, in the same shape;
6. private free helper functions;
7. `#[cfg(test)] mod tests`.

Inside an `impl`: constructors (`new`, `with_*`, `from_*`) → queries
(`&self`) → commands (`&mut self`) → consuming methods (`self`). Public before
private.
